01 Overview

Dhare Foundation plants and maintains trees across Karnataka — including the "Green Ring Bengaluru" greenbelt initiative — using both traditional plantation and the dense Miyawaki method. This site is its public face and its internal record-keeping tool: visitors learn about the work, register as volunteers, or request saplings; staff log in to record plantation sites, manage registrations, and control a few site-wide settings.

The codebase is a single Next.js application serving both halves. Public pages are internationalized (English and Kannada); the staff-facing admin system is a separate, flat set of routes layered on top, sharing the same database.

05 Donations Bank transfer only

A Razorpay online-checkout integration was built, tested, then deliberately reverted.

The Donate section shows three suggested tiers and a custom-amount option; every button opens a modal with bank transfer details (account number, IFSC, branch). No transaction is recorded today — it's informational only. Rebuilding this with Razorpay, including a receipt/confirmation step and donation record-keeping, is the next planned feature.

06 Staff system

One login page, two roles, a shared session model.

Login & sessions

/login presents role tabs (Admin / Site Coordinator) over a single username-or-email + password form. Accounts live in staff_users (bcrypt-hashed passwords), created from the admin dashboard or via scripts/create-staff-user.mjs. A session is a signed HMAC-SHA256 cookie carrying { userId, role, name }, verified on every request to /admin or /coordinator.

07 Database

Supabase Postgres, accessed only via the service-role key from server code. Row-level security is enabled on every table; public read policies exist only where the public site actually displays the data.

Plantation photos/videos live in the plantation-media Storage bucket (public read, for future public display).

No migration tool supabase-setup.sql is an append-only log of statements, pasted into the Supabase SQL Editor by hand. New changes get a new dated section at the bottom, written to be safe to re-run (if not exists, on conflict do nothing) — history is never rewritten.

08 Deployment

Every push to master deploys straight to production. There is no staging environment and no CI gate — the checklist below is the substitute.

npx tsc --noEmit   # typecheck
npm run build      # full production build

New environment variables must be added in Vercel before the code that needs them ships — otherwise the affected pages error immediately after deploy.

Dev and production share one Supabase project There is no separate staging database today. Anything created while testing locally — registrations, plantation sites, staff accounts — is real, live data.

09 Limitations & roadmap

What's known, on purpose, to be incomplete — so it doesn't get mistaken for an oversight.

Razorpay donations — planned next: online checkout with a receipt/confirmation step and donation record-keeping, replacing the current bank-transfer-only modal.
No staging database — dev and production currently share one Supabase project; splitting these would remove the risk of test data reaching the live site.
No automated tests — verification today is tsc + a production build + manual browser checks. playwright is present only for an ad-hoc screenshot script, not a test suite.
Plantation media is add-only — editing a site can add more photos/videos, but not yet remove or replace existing ones.
Site Coordinator features — the dashboard exists and authenticates correctly, but has no coordinator-specific tools yet.
Coordinator self-registration — currently admin-registers-only. A self-registration-with-approval flow is a moderate addition if the number of coordinators grows, reusing the existing account and role-gating infrastructure.
